# 1.3.0 — intake, and a knowledge base that stays true

## What changed

Installation is no longer done when the files are in place. It opens six intake work orders,
each with a spec that ships complete and a suite that proves the step, and the project is
operational only when all six have closed on executed evidence. `acp intake inventory`
classifies the repository before anything is adopted. The knowledge base is the eight-phase
repository analysis run against the project's own code, with a source index that records a
content hash per cited file; `acp kb status` reports what is current, stale, or broken,
`wo close` names the profiles a change touched, and `acp check` carries the rule into CI.

Also in this release: two complete behavioural example suites, the case against stubbed
end-to-end tests restored to the methodology, and three assertion helpers.

## What was found, and how

The intake steps, the adoption path, and the baseline all come from the field report of a
real adoption into a mature monorepo (see 1.2.0). The knowledge base was already shipped as the
documentation lifecycle for code you did not write; a review of that report found it was
never run against the project itself and was reachable only from Claude Code. The
in-place adoption path came from the first inventory run, which proposed adopting the
pipeline's own intake work orders.

## Still open

  project's own release notes are the next release.
- The knowledge base is built by an agent; the tool knows when it is stale and says so, but
  does not rewrite a profile.
- Environment pinning for baselines remains the project's responsibility.
